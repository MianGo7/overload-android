# Development journal

A chronological record of the work, one entry per session, written on the same
day. Each entry states what was built, what was decided, which problems
occurred and how they were resolved. These entries are the main source for the
process criterion and for the lessons learned chapter, so difficulties are
recorded as they occurred rather than summarised comfortably afterwards.

---

## 2026-09-13

The repository skeleton was created. It comprises a Gradle build with a
version catalogue and a committed wrapper, the Android application module, the
domain layer together with its unit tests, the Room data layer, the manual
dependency container, five activities with their Compose screens and view
models, and the documentation set under `docs/`. The specification was fixed
before any code was written, namely task 1 of the examination task, training
volume as the application domain, Jetpack Compose with several activities, and
Room with a hand written dependency container rather than a framework.

No Gradle synchronisation had been performed at this point, so nothing had yet
been compiled. Dependency versions were therefore pinned conservatively to
combinations known to work together, and the user interface was restricted to
stable Compose interfaces. The intention was that the first synchronisation
would surface at most a small number of failures rather than several unrelated
ones at once.

The planning documents followed later the same day: the personal checklist in
`next-steps.md`, the backlog, and a local summary of what the examination
requires. That summary is excluded from version control through the
`*.local.md` rule, because IU holds the copyright on its examination tasks and
objects to their publication on third party platforms, and the repository will
be linked in the report.

The next step was the first synchronisation.

## 2026-09-14

Opening the project in Android Studio triggered the Android Gradle plugin
(AGP) upgrade assistant, which raised Gradle to 9.6.0, AGP to 9.4.0, Kotlin
to 2.2.10 and Kotlin Symbol Processing (KSP) to 2.3.6, leaving Room at 2.6.1.
The first build failed in `kspDebugKotlin` with `unexpected jvm signature V`,
a known error produced when KSP2 meets an annotation processor written
before KSP2 existed; Room only gained KSP2 support in version 2.7.0, so
raising it to 2.8.5 fixed the build (ADR-0010). The assistant also left
several `android.*` compatibility flags and two Kotlin warnings about a
future change to annotation targets. The unnecessary flags were removed, the
recommended `-Xannotation-default-target=param-property` option was adopted
in place of the deprecated `kotlinOptions` block, and a redundant activity
label plus an unnecessary `mipmap-anydpi-v26` qualifier were cleaned up.
`android.builtInKotlin` and `android.newDsl` were left in place as backlog
item B11.

A further `lintDebug` pass found twelve dependency currency warnings.
Every one was raised to its current stable release, Kotlin to 2.4.20, KSP to
2.3.12, the AndroidX and Compose libraries, the Gradle wrapper and
`compileSdk` included, recorded as ADR-0011. Raising Kotlin despite an open
issue in the KSP tracker suggesting version 2.4.0 was not yet fully
supported was verified by running the build rather than by trusting the
tracker. A Pixel phone was then paired over wireless debugging and
`installDebug` succeeded, closing out backlog item B0.

B1 followed: `GoalViewModelTest` and `LogEntryViewModelTest` cover the
listed validation rules against two new in memory fakes. Two
`GoalViewModelTest` cases initially failed because the view model was built
as a property initialiser, before JUnit's `@Before` installed the test main
dispatcher, and `GoalViewModel`'s `init` block already launches a coroutine
on `viewModelScope`. Moving construction into `@Before` resolved it, and
acceptance criterion AC6 moved to done.

The continuous integration (CI) pipeline was then found failing with a
toolchain download error. The cause was `gradle/gradle-daemon-jvm.properties`,
generated by Android Studio and pinning the Gradle daemon itself to a
JetBrains Runtime version 21 that only resolved locally because that runtime
happened to already be installed. The file was deleted, since a green local
build had never actually proven a green pipeline.

B2 followed next, taken ahead of priority order since it unblocks every
report screenshot. `SeedDataGenerator` builds seven weeks of training
history with one deliberately light week timed so the deload advisor reports
the block complete on the most recent week, verified against
`VolumeCalculator` and `DeloadAdvisor` by test rather than by hand
arithmetic. A debug only "Seed demo data" action wires it to the dashboard.
An Android emulator, a Pixel 10 Pro XL, was set up in Android Studio to
reduce reliance on a personal phone for verification, and the seed action
was confirmed end to end, taking the dashboard from empty to 92 percent of
the weekly goal with the deload card shown and all seven weeks visible in
history.

B11 closed the day. Running with `-Pandroid.debug.obsoleteApi=true` showed
both remaining compatibility flags traced to one cause, the
`org.jetbrains.kotlin.android` plugin itself calling the deprecated variant
application programming interface, so dropping that plugin for AGP's
built in Kotlin support removed both flags together and the `srcDirs`
deprecation with them. A further, previously unnoticed deprecation on
`android.dependency.excludeLibraryComponentsFromConstraints` was fixed the
same way, and the configuration cache was enabled and verified, recorded as
ADR-0012. All three Gradle commands now run with no deprecation warnings.
Verifying on the emulator briefly suggested the seed action was duplicating
data sevenfold, which traced to Room's write ahead log file being excluded
from a raw database copy rather than to a defect, confirmed by a clean
single tap test read through the app itself. Worth remembering for the
report: a raw Room database file copy is not trustworthy evidence on its
own.
